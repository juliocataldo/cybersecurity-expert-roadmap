Containers e deploy

O pipeline entrega uma imagem assinada. Depois disso ainda falta rodá-la e colocá-la no ar sem derrubar ninguém. Aqui estão as duas peças, em diagrama: o que acontece quando você roda um container (Docker e Kubernetes) e as três formas de trocar a versão em produção (Rolling, Blue-Green e Canary), com o que cada uma muda na segurança.

01Docker x Kubernetes

Os dois rodam containers, mas resolvem problemas diferentes. O Docker roda um container numa máquina, quando você manda. O Kubernetes recebe um estado desejado ("quero 3 réplicas da v2") e fica, o tempo todo, fazendo o cluster inteiro bater com ele.

  • Imperativo x declarativo No Docker você diz faça isto. No Kubernetes você diz quero isto, e os controllers corrigem sozinhos o que sair do lugar: um Pod que morre é recriado, um node que cai tem os Pods remarcados em outro.
  • O Kubernetes não usa o Docker Desde a versão 1.24 o kubelet fala direto com um runtime compatível com CRI (containerd ou CRI-O), que por baixo também usa o runc. A imagem que você constrói com Docker roda igual, porque segue o padrão OCI.
  • Mesmo kernel Nos dois casos o container é um processo isolado por namespaces e cgroups, dividindo o kernel com o host. Isolamento não é uma VM: um escape de container cai no node.

02Rolling x Blue-Green x Canary

Três jeitos de colocar uma versão nova no ar sem tirar a aplicação do ar. Todos começam no mesmo merge; o que muda é quantos usuários veem a versão nova, e quando, e quanto custa voltar atrás.

03O que muda na segurança

Onde um atacante olha em cada peça do diagrama, e o controle que fecha a porta.

  • Socket do Docker Quem fala com o dockerd é root no host. Nunca monte /var/run/docker.sock num container (é o atalho clássico de escape) e prefira o modo rootless onde der.
  • API Server É a porta da frente do cluster: RBAC com o mínimo de permissão, sem acesso anônimo, endpoint privado e audit log ligado. Um cluster-admin esquecido numa ServiceAccount vale o cluster inteiro.
  • etcd Guarda os Secrets, que por padrão são só base64. Criptografia em repouso, mTLS e acesso apenas pelo API Server; para segredos de verdade, um cofre externo (Azure Key Vault, Google Secret Manager) com External Secrets.
  • kubelet e Pods kubelet com autenticação e autorização (porta 10250 nunca exposta), Pod Security Admission no perfil restricted e NetworkPolicy com negar tudo por padrão.
  • Só sobe o que o pipeline aprovou Imagem referenciada pelo digest, não pela tag, e assinatura verificada na admissão (Kyverno ou Sigstore policy-controller). Vale para as três estratégias.
  • Rolling v1 e v2 atendem ao mesmo tempo: a API e o banco precisam aceitar as duas (migração expand/contract). A readiness probe é o gate; probe que sempre responde 200 libera versão quebrada.
  • Blue-Green O ambiente parado continua sendo superfície de ataque e continua com credenciais. Corrija os dois, revogue o que o Blue usava quando ele sair, e cuidado com migração de banco irreversível: ela impede a "volta instantânea".
  • Canary Também limita o raio de uma falha de segurança: inclua 401, 403 e bloqueios do WAF nas métricas de análise. Se o roteamento for por cabeçalho ou cookie, o usuário não pode escolher cair no canary.
  • Rollback não é neutro Voltar para a versão anterior de um patch de segurança reabre a CVE. Rollback é para a última versão boa conhecida, e a decisão de voltar um patch passa por segurança.

04Na prática: Rolling seguro e Canary com análise

Dois manifestos para estudar linha a linha. Os nomes, o registry e o digest são de exemplo.

deployment.yaml Kubernetes · rolling update

apiVersion: apps/v1
kind: Deployment
metadata:
  name: checkout
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%          # sobe 1 Pod novo por vez
      maxUnavailable: 0      # nunca fica com menos de 4 atendendo
  selector:
    matchLabels: { app: checkout }
  template:
    metadata:
      labels: { app: checkout }
    spec:
      automountServiceAccountToken: false   # o app não fala com o API Server
      securityContext:
        runAsNonRoot: true
        seccompProfile: { type: RuntimeDefault }
      containers:
        - name: app
          # pelo digest: a tag pode ser reapontada, o digest não
          image: registry.example.com/checkout@sha256:<digest-assinado>
          ports: [{ containerPort: 8080 }]
          readinessProbe:        # o gate do rolling: sem ela, Pod quebrado recebe tráfego
            httpGet: { path: /ready, port: 8080 }
            periodSeconds: 5
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: { drop: ["ALL"] }
          resources:
            requests: { cpu: 100m, memory: 128Mi }
            limits: { memory: 256Mi }

rollout.yaml Argo Rollouts · canary

apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: checkout
spec:
  replicas: 10
  strategy:
    canary:
      analysis:              # roda durante todo o canary; se falhar, aborta e volta a 0%
        templates: [{ templateName: erro-e-latencia }]
        startingStep: 1
      steps:
        - setWeight: 5
        - pause: { duration: 10m }
        - setWeight: 25
        - pause: { duration: 10m }
        - setWeight: 50
        - pause: { duration: 10m }
  # selector e template iguais aos do Deployment acima
Por que maxUnavailable: 0?

Com 0, o Kubernetes só derruba um Pod v1 depois que um v2 ficou pronto. A capacidade nunca cai abaixo das réplicas pedidas, ao custo de precisar de espaço no cluster para o Pod extra (o maxSurge).

O que o AnalysisTemplate deveria medir?

O SLI do serviço: taxa de 5xx e latência p95 da versão canary, comparadas com a estável. Somando segurança: picos de 401/403 e de bloqueios do WAF, que indicam regressão de autenticação ou autorização. O alerta por burn rate da página de SRE usa as mesmas métricas.

05Perguntas para fixar

Tente responder em voz alta antes de abrir.

Se o Kubernetes não usa o Docker, por que ainda se fala em Docker?

Porque o Docker continua sendo a ferramenta mais comum para construir imagens e rodar containers na máquina do desenvolvedor. A imagem segue o padrão OCI, então qualquer runtime compatível roda. O que saiu do Kubernetes foi só o dockershim, a ponte entre o kubelet e o dockerd.

Tenho uma migração de banco que remove uma coluna. Qual estratégia uso?

Nenhuma resolve sozinha. Separe em etapas (expand/contract): primeiro publique uma versão que não usa mais a coluna, com qualquer estratégia; só depois, num deploy separado, remova a coluna. Assim v1 e v2 convivem com o mesmo banco e o rollback continua possível.

Canary e feature flag são a mesma coisa?

Não. Canary divide o tráfego entre versões do binário; feature flag liga uma funcionalidade dentro da mesma versão, por usuário ou grupo. Elas se completam: o canary protege contra o deploy quebrado, a flag permite desligar uma funcionalidade sem novo deploy.

Um Pod sem readiness probe num rolling update: o que acontece?

O Kubernetes considera o Pod pronto assim que o container inicia e já manda tráfego, mesmo que a aplicação ainda esteja subindo ou quebrada. O rollout avança, derruba os Pods v1 e o erro chega a todos. A readiness probe é o que transforma o rolling num gate.

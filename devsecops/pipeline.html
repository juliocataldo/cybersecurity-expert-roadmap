Um pipeline seguro, comentado

Um exemplo em GitHub Actions para um projeto Node.js com contêiner. A ideia vale para Azure DevOps, GitLab ou Jenkins: muda a sintaxe, não os estágios. Use como ponto de partida, não como receita fechada.

Antes de copiar: troque cada <sha-do-commit> e <versão> por valores fixos que você conferiu, e confira a sintaxe de cada ferramenta na documentação da versão escolhida; as opções mudam entre versões.

01Código, dependências e segredos

Roda em todo pull request e em todo push na main. Os jobs são independentes, para o retorno chegar rápido.

.github/workflows/devsecops.yml parte 1

name: devsecops
on:
  pull_request:
  push:
    branches: [main]

# Mínimo por padrão: cada job pede só o que precisa.
permissions:
  contents: read

jobs:
  segredos:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<sha-do-commit>   # v4, fixado por SHA
        with:
          fetch-depth: 0                          # histórico completo
          persist-credentials: false
      - name: Segredos no histórico do Git
        run: >
          docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:<versão>
          git /repo --redact

  codigo-e-dependencias:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<sha-do-commit>
        with:
          persist-credentials: false
      - name: SAST (Semgrep)
        run: >
          docker run --rm -v "$PWD:/src" semgrep/semgrep:<versão>
          semgrep scan --config p/default --error
      - name: SCA (dependências do Node)
        run: |
          npm ci --ignore-scripts
          npm audit --audit-level=high
      - name: Dependências, segredos e IaC (Trivy)
        run: >
          docker run --rm -v "$PWD:/src" aquasec/trivy:<versão>
          fs --scanners vuln,secret,misconfig
          --severity HIGH,CRITICAL --exit-code 1 /src
      - name: SBOM (CycloneDX)
        run: >
          docker run --rm -v "$PWD:/src" aquasec/trivy:<versão>
          fs --format cyclonedx --output /src/sbom.cdx.json /src
O que cada passo faz e por que está ali?
  • Segredos no histórico: o Gitleaks olha todos os commits, não só os arquivos atuais; uma chave apagada continua no histórico. --redact evita que o valor apareça no log.
  • SAST: o Semgrep procura padrões inseguros no código (SQL montado com concatenação, eval, desserialização). --error faz o passo falhar se houver achado.
  • SCA: npm ci --ignore-scripts instala exatamente o que está no lockfile sem rodar scripts de instalação (um vetor comum de pacote malicioso); npm audit falha a partir de severidade alta.
  • Trivy: num só passo, vulnerabilidades de dependências, segredos nos arquivos e configuração insegura de IaC e Dockerfile.
  • SBOM: a lista de componentes no formato CycloneDX. Quando sair uma CVE nova, ela responde se você está afetado sem precisar rodar nada de novo.
Por que persist-credentials: false no checkout?

Por padrão, o checkout guarda o token do job na configuração do Git do runner. Qualquer passo seguinte, inclusive uma ferramenta comprometida, poderia usá-lo. Se o job não precisa fazer push, não deixe o token lá.

02Imagem, varredura e assinatura

Só roda se os jobs anteriores passarem. É o único job que pede permissão de escrita, e só para o que precisa.

.github/workflows/devsecops.yml parte 2

imagem:
    needs: [segredos, codigo-e-dependencias]
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write     # publicar no registry
      id-token: write     # assinatura keyless via OIDC (sem chave guardada)
    steps:
      - uses: actions/checkout@<sha-do-commit>
        with:
          persist-credentials: false
      - name: Build
        run: |
          docker build -t app:${{ github.sha }} .
          docker save app:${{ github.sha }} -o app.tar
      - name: Varredura da imagem (sem montar o docker.sock)
        run: >
          docker run --rm -v "$PWD:/src" aquasec/trivy:<versão>
          image --input /src/app.tar
          --severity HIGH,CRITICAL --exit-code 1
      # ... login no registry e push (id: push); depois, assinar pelo digest, nunca pela tag:
      - name: Assinatura (Sigstore Cosign)
        run: cosign sign --yes ghcr.io/minha-org/app@${{ steps.push.outputs.digest }}
Por que exportar a imagem em vez de montar o docker.sock?

Montar o socket do Docker dentro de um contêiner dá a ele controle total do Docker do host, o equivalente a root. Exportar a imagem para um arquivo e passar com --input dá o mesmo resultado sem esse privilégio.

Por que assinar pelo digest e não pela tag?

A tag (:latest, :1.4) pode ser movida para outra imagem; o digest (@sha256:...) identifica exatamente aquele conteúdo. Com id-token: write, o Cosign assina sem chave guardada (keyless): a identidade vem do OIDC do GitHub e fica registrada num log público de transparência.

03O que bloqueia, o que avisa

Bloquear tudo faz o time contornar o pipeline. Uma política de partida, para ajustar com dados:

  • Bloqueia Segredo encontrado; vulnerabilidade crítica ou alta com correção disponível em dependência de produção; configuração crítica de IaC (bucket público, porta de administração aberta para a internet); imagem com crítica corrigível.
  • Avisa no PR Achados de SAST de severidade média, vulnerabilidades sem correção disponível, dependências de desenvolvimento.
  • Exceção Por escrito, com motivo, dono e prazo, revisada no vencimento. Nunca desligar a regra para o repositório inteiro.
  • Falha do scanner Se a ferramenta não rodar (fora do ar, erro de configuração), o job falha. Gate que passa quando não verificou nada é pior que não ter gate.

# Toda exceção tem motivo, dono e prazo. Revisar no vencimento.
# CVE-AAAA-NNNNN: a função vulnerável não é chamada pelo app (analisado no PR #123).
# Dono: time-pagamentos. Revisar até 2026-12-31.

04Proteger o próprio pipeline

O pipeline tem acesso ao código, aos segredos e à produção: é um alvo valioso. O OWASP Top 10 CI/CD lista os riscos; na prática, estes controles cobrem a maior parte:

  • Permissões mínimas Declare permissions no topo com contents: read e libere o resto só no job que precisa. Configure também o padrão do repositório e da organização como somente leitura.
  • Actions fixadas por SHA Tag pode ser movida por quem controla o repositório da action. Em março de 2025, as tags da action tj-actions/changed-files foram apontadas para código malicioso que expôs segredos em logs de milhares de repositórios (CVE-2025-30066). Quem fixava por SHA não foi afetado.
  • Atualização das actions Fixar por SHA não é congelar: o Dependabot atualiza actions também, com pull request revisável.
  • OIDC em vez de chaves Para AWS, Azure e GCP, use federação OIDC com role restrita ao repositório e à branch. Nada de chave de nuvem guardada como segredo.
  • Ambientes com aprovação Segredos de produção só num environment com revisores obrigatórios e restrito à branch main.
  • Cuidado com pull_request_target Esse gatilho roda com permissões e segredos do repositório. Nunca faça checkout e execução do código do pull request nele; um fork pode alterar o código e roubar os segredos.
  • Proteção da branch Rulesets com revisão obrigatória, status checks obrigatórios e CODEOWNERS para .github/workflows/. Sem isso, qualquer pessoa com escrita desliga o gate.
  • Runners Runner self-hosted nunca em repositório público, e de preferência efêmero: um job não pode deixar nada para o próximo.

.github/dependabot.yml atualizar actions e pacotes

version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly

05Perguntas para fixar

Tente responder antes de abrir.

O SAST encontrou 400 achados no primeiro dia. E agora?

Não bloquear ainda. Medir quais regras geram mais falso positivo, desligar ou ajustar essas, tratar os verdadeiros por criticidade e só bloquear achados novos (no diff do pull request), para o passivo não travar a entrega.

Uma chave de API apareceu num commit antigo. Apagar o arquivo resolve?

Não. A chave continua no histórico e pode já ter sido copiada. Primeiro revogar e trocar a chave; depois avaliar se ela foi usada (logs do provedor). Reescrever o histórico é opcional e vem por último.

O scanner de dependências ficou fora do ar e o build passou. Está certo?

Não: é falhar aberto. O passo precisa falhar quando não consegue verificar, e a equipe decide conscientemente liberar, com registro.

Por que não usar a tag @v4 das actions, se é mais simples?

Porque a tag pode ser movida para outro código. O SHA identifica exatamente o que foi revisado, e o Dependabot cuida da atualização.
